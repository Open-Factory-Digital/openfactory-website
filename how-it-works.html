How it actually works

Everything on this page is measured, and every claim carries the command or the incident that proves it. This is the deep-dive for anyone deciding whether to trust it, not the version written to be easy to read.

Provider-neutral by design

Connects to what you already run

OpenFactory sits between the board where a ticket already lives and the coding agent that works it. Each connection is a registry value, not a fork: swap the tracker without touching the harness, or swap the harness without touching anything else.

on any impediment

The tech-lead steps in

Parks the ticket instead of retrying blindly, and routes the failure to whoever (or whatever) actually fixes it. See how it manages that risk.

requirements in

The product role, from Slack

Talks to the client, proposes what enters the queue, and turns a conversation into a tracked commitment. See roles.

Four roles, three of them judge

Who actually does what

One role writes code. The other three decide what to build, whether a stall needs a person, and whether a diff is good enough to merge. Which engine runs a role is configuration, per project and even per role.

The executor writes the diff

Works the ticket end to end inside a sandbox already proven to build the project, test-driven, against the project's own gates. Which model runs it is a registry value: Claude Code, Codex, Kimi, or OpenCode.

The reviewer runs on a second engine

Sees the specification, the diff, and the gate results, but never the author's reasoning, and returns a decision, a score, and findings tied to acceptance criteria. It can run on a different harness and model than the one that wrote the code, because a model grading its own work is not a review.

The tech-lead is on call, not on demand

When a job stalls, it clones the repo and reads the failure against the real code, then classifies it by what actually remedies it: resolving what it safely can, and putting a real decision in front of a person for the rest.

Letting an agent act on its own is the risky part of "autonomous." See exactly where the leash is.

The product role proposes. It never assumes.

Talks to the client in their own channel, reads the board, and proposes what enters the queue, citing the requirement behind every claim. Reading a codebase produces an observation, never a requirement: what the code does isn't automatically what it should do, and only a person moving something from observed to accepted creates a promise.

Reachable from Slack today. Its own surface is still being built; see limits.

The risk of acting alone

Autonomy needs a leash

Letting a system act without a human approving every step is exactly the part that should worry you. Here's the incident that shaped how the tech-lead decides, and exactly where the leash is.

Incident · 2026-07-26 · ticket #478

GitHub throttled the API. That's the most trivially self-healing failure a system can have: the window resets, and the same call succeeds. Instead, the factory parked the ticket, held the floor for eighteen hours, ran nothing else, and told nobody. The one Slack message a park should have produced never fired, because the diagnosis meant to write it couldn't run either.

That incident is why the tech-lead now asks one question before anything else: what actually fixes this?

ClassExampleWho resolves it
transientAPI throttling, a network blipthe factory: waits out the window, retries
credentiala token revoked or exhaustedthe factory: rotates, escalates only if the whole pool is bad
environmenta missing permission, a broken imagea named person, with the specific thing to change
codethe change is genuinely wronga human engineer, with the diagnosis
requirementthe ticket is ambiguous or contradicts itselfthe product role
unknownit cannot tella human, told plainly that it cannot tell

The asymmetry is deliberate

Waiting costs nothing. A throttled call retried after its window spends no agent, no tokens, no money, so that bound can be generous. Re-running an agent is a different decision: a flaky gate or a failed execution is real money, and three "helpful" retries on a ticket that was never going to pass is how a factory quietly triples its bill.

So the budget is per failure class, not global, and a remedy that hasn't worked twice is not a remedy. It's just a loop with a good story. unknown never degrades toward retry: repeating a failure nobody understood just burns spend on something structurally broken while looking like progress.

What it may never do

  • Resurrect work a human already skipped.
  • Retry anything classified unknown, code, or requirement.
  • Exceed its budget, silently or otherwise. An exhausted budget is itself an escalation.
  • Touch production. Releases stay human-authenticated: identity and password, always.
read

Free for anyone in the project's Slack channel. Ask "what's the status of X" and get an answer. No gate.

write

resume / skip only for a Slack user on that project's allowlist. Empty by default, so nobody can act until a project opts in.

production

Never actionable from Slack, full stop, not even for an admin. An unauthorized attempt is told plainly and logged, never silently executed.

Classification will sometimes be wrong. The bias is deliberate and asymmetric: wrong toward retry wastes money and delays a real escalation, while wrong toward escalation only wastes a person's attention. The cheap-first ordering means the common mistake costs a wait, not a bill. A confident wrong remedy is worse than no remedy, so every action says what it did and what it tries next if that fails.

Beyond "an agent with repo access"

What makes it different

It refuses to work in the dark

Nothing runs until the box is proven: the project's own image, its setup and its gates, executed once with no agent and no tokens spent. A box that cannot build the project is a fact you want before an agent spends four hours discovering it.

It never stalls in silence

Every stall either self-heals within a bound or asks a human with executable options: not a logged warning, but a question on the card, with wait / merge / skip as choices the human picks and the factory then executes. The invariant is enforced by tests that treat "went quiet" as a bug.

Failure never looks like an answer

Every port separates an unreadable result from an empty one.

None = I could not read. [] = I read it, and there is nothing.

The independent review is a real second agent

It sees the specification, the diff, and the gate results, but never the author's reasoning, and returns a decision, a score, and findings tied to acceptance criteria. It has rejected work for the right reasons: a diff that met its criteria but landed in the wrong repository was caught by the reviewer, not by a human.

Merging is policy, not vibes

merge_policy: human opens the PR and waits. auto merges only when gates are green, the review did not reject, and no high-risk component was touched. A quality floor refuses a paid agent pass on a project that declares no gates at all.

It triggers; it never deploys

The platform merges or tags and then observes the client's own pipeline. Deployment stays with the client's credentials, in the client's CI. Production promotion requires a human action with a password, always.

Proof, not marketing

Three claims, and the command that proves each one

Everything on this page is measured, and each claim carries the command that proves it. A platform whose pitch is "never a silent failure" cannot open with a claim nobody checked.

01

A provider is configuration, not a code change

Nine axes dispatch through registries: tracker, board, forge, CI/environment, harness, sandbox, events, metrics. The axes are independent: Jira for tickets and GitHub for code is a two-line registry entry, not a fork. An unknown provider raises at startup naming what is supported. It never falls back to a default, because a deployment pointed at the wrong vendor should surface as the configuration mistake it is, not as a confusing permissions error.

Proven end to end, not just wired. GitHub: a ticket to a merged PR, and a live client running in production. Jira: requirement → PR → merge → the client's GitHub Actions deploy, observed. Azure DevOps: a work item to a reviewed PR in Azure Repos, zero GitHub anywhere, including a three-repository product where the card names its own repo.

02

Multi-harness, and the model is per project and per role

Four coding agents are supported behind one contract, and the choice is a registry value. The reviewer being a different engine from the author is the point of the per-role axis: a model grading its own work is not a review.

.sdlc/project.yaml 
harness: opencode
model:
  executor: eu.anthropic.claude-sonnet-5
  reviewer: eu.anthropic.claude-haiku-4-5   # a cheaper, independent second opinion

Routes are configuration too: Anthropic direct, Amazon Bedrock, a corporate gateway, Vertex. An enterprise whose security team requires everything inside their own AWS account changes one value, no fork, no special build. This platform's own tickets have been written by Claude Code and by OpenCode, both over Bedrock, in eu-west-2.

Deployment

It runs on your machines

boto3 is not a core dependency; every cloud import is function-level; each observability axis keeps a cloud-free option; and a test blocks every cloud SDK in a subprocess and imports the core for real to prove it.

AWS, Azure, and the rest are add-ons: the platform without them is complete, not hobbled. Remove the Fargate launcher and jobs still run in local containers. Vendor coupling is legitimate exactly where the client already lives (reading their Jira, observing their pipeline), and nowhere else.

docker compose up
Prove the core needs no cloud

Governance

Extending it

A new provider is one module plus one registry row. It is not accepted on that basis alone: a published conformance suite checks the contract, and every adapter is runtime-checked against its Protocol so a half-implemented one cannot ship and be discovered in production.

Conformance is also how the name is governed. The code is Apache-2.0 and anyone may fork it; the OpenFactory name is not licensed with it, and only builds that pass the published conformance suite may use it. Permissive licence, defended mark, conformance as the gate.

Check a new provider 
openfactory conformance-adapter tracker my_pkg.my_tracker:MyTracker
openfactory conformance <project>

What it does not do yet

Stating limits is not weakness; it is the same discipline as the rest. A visitor who finds a gap after adopting is a visitor who stops believing the parts that were true.

  • The product/requirements role is only reachable from Slack today. It sweeps and reconciles without it, but the conversational half (proposing, accepting, versioning a requirement) lives in the Slack package and does not yet have its own surface.
  • Onboarding a legacy codebase is manual. The platform verifies what you declare; it does not yet read your repository and propose it. That is being built, and it is the difference between a greenfield happy path and the codebase you actually have.
  • The knowledge map reads Python, TypeScript/JavaScript and C#. Other stacks are mapped structurally or not at all. The map now declares which extensions it did not understand, rather than looking complete.
  • GitLab and Bitbucket are not implemented. The seam is proven by three providers on the tracker axis and two on the forge axis; the fourth is a module and a row, not a redesign.
